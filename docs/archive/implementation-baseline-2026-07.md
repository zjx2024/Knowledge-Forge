# Knowledge Forge implementation baseline

## Goal

Build a self-contained, multi-project knowledge base and knowledge graph platform.
RAGFlow is no longer a runtime dependency. PostgreSQL stores metadata, chunks,
embeddings, entity mentions, canonical entities, relation assertions and schema
versions. HugeGraph stores the navigable graph. Ollama provides embedding and
structured extraction models.

## Stable architecture

1. Parse uploaded DOCX, PDF, Markdown and text into heading-aware sections and
   bounded chunks.
2. Generate chunk embeddings with Ollama and persist them in pgvector. HNSW
   retrieves project/model-scoped candidates in PostgreSQL; lexical overlap
   reranks those candidates while exact substring hits are included explicitly.
3. Every project starts from one generic logical schema. Low-information chunks
   are filtered before section-stratified, embedding-diverse representative
   chunks are reviewed in batches. Candidate types are consolidated and must
   pass confidence, evidence-diversity, duplication and addition-count gates.
   Cross-document embedding novelty avoids redundant reviews; safe additions
   create a new logical schema version. Physical HugeGraph labels remain generic
   and stable.
4. Extract entity mentions and relation assertions per chunk. Resolve mentions
   to project-scoped canonical entities using normalized names, aliases and
   embedding similarity. Keep document/chunk provenance on every assertion.
5. Use the dedicated physical HugeGraph graph `knowledge_forge`, separate from
   the existing `hugegraph` and `test` graphs. Write project-isolated
   `KFDocument`, `KFChunk`, and `KFEntity` vertices plus `kf_contains`,
   `kf_mentions`, and `kf_related` edges into it.
6. Soft deletion removes the document contribution from retrieval and graph
   assertions, then retires canonical entities that no remaining document uses.
7. All long-running operations use PostgreSQL-backed jobs so progress survives
   page navigation and process restarts.

## Safety rules

- No destructive physical schema changes are generated by the LLM.
- Logical schema changes are append-only and versioned.
- Low-confidence entity merges remain separate; provenance is never discarded.
- Project ID/key is required on every vector and graph record.
- Re-ingesting a document replaces that document's derived records idempotently.

## Vector storage baseline

pgvector with model-and-dimension-specific HNSW indexes is the production
baseline. The legacy PostgreSQL array column remains temporarily available for
rollback and entity-resolution compatibility; user-facing retrieval never
loads every project vector into application memory.
