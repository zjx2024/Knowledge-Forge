# 实体关系抽取与归一质量评估

## 1. 文档目的

本文档总结 Knowledge Forge 当前实体与关系抽取、实体归一、关系复核和图谱发布链路的
实际能力与主要问题，并给出后续优化顺序和验收指标。评估将“代码已经实现的保护”与
“运行效果已经达到生产要求”分开描述。

评估日期：2026-07-22。

评估范围：

- 当前代码分支 `feat/graphrag-community-shadow`，评估时 HEAD 为 `2b7337e`；
- 当前 PostgreSQL 运行库中的有效项目数据和最近一次 AI Governance 入库日志；
- 当前 control 抽取与发布链路，以及仍处于 shadow 状态的 P1/P2 实体、关系策略；
- GraphRAG 社区检测仅作为已发布图的下游组织能力，不视为抽取或归一修复手段。

当前运行容器的数据库结构早于最新代码迁移，尚未包含 `relation_candidates`、
`graph_generation` 等新字段或表。因此，运行库可以证明现有 control 链路的实际效果，
但不能用来证明最新 shadow 策略已经在生产链路启用。

## 2. 当前处理链路

### 2.1 实体与关系抽取

当前 control 链路按知识块执行以下步骤：

1. LLM 从知识块原文中抽取实体提及和关系候选；
2. 实体提及携带原文 `surface/name`、类型、字符起止位置和证据上下文；
3. 信息量较高但关系为空的知识块可执行一次针对性补抽取；
4. 规则校验实体是否真实出现、关系端点是否存在、证据是否能在原文定位；
5. 对不确定关系构建局部候选并执行批量 LLM 复核；
6. 只有满足发布条件的关系才能进入正式关系图。

关系候选只在当前知识块和局部上下文中生成，避免对项目全部实体进行平方级两两组合。
候选还会受实体类型组合、关系提示词、每个源实体候选数、每个知识块候选数和每批复核数
约束。超出容量、缺少响应、最终失败或隔离的候选必须使快照
`coverage_complete=false`，从而阻止评估、质量门禁和生产激活。

### 2.2 实体归一

实体归一采用分层候选召回，而不是把新实体与项目全部实体逐一比较：

```text
稳定 mention_key 复用已有 occurrence 归属
→ 规范名称和别名精确匹配
→ PostgreSQL 名称/pg_trgm 候选
→ pgvector Top-K 语义候选
→ 类型、名称、编号和版本规则过滤
→ reranker 重排
→ 必要时由 LLM 对少量候选裁决
→ 无可靠候选时创建新规范实体
```

最终接受前会再次检查 cannot-link，且检查范围覆盖 redirect 前的旧节点和当前根节点。
已有 `mention_key` 的重试优先复用当前有效 assignment，避免同一 occurrence 因模型输出
变化而漂移。名称规范化使用 Unicode casefold，精确位置采用半开区间，不回退到第一次
字符串匹配。

### 2.3 关系发布和社区检测

正式关系图采用 fail-closed 发布规则：证据不完整、复核未覆盖、策略版本不一致或图快照
不完整时不允许晋级。P1/P2 新策略继续处于 shadow，只生成隔离结果和评估数据，不替换
control 结果。

GraphRAG 3.1.1 BYOG 社区模块读取已经发布的正式关系图，生成 shadow 社区、成员和聚合边。
它可以组织和概括已有图结构，但不能修复错误实体边界、漏关系、错关系或漏合并。

## 3. 运行数据快照

以下统计只包含 `is_deleted=false` 的有效数据：

| 项目 | 文档 | 知识块 | 实体提及 | 规范实体 | 关系 |
| --- | ---: | ---: | ---: | ---: | ---: |
| ICP-fault-knowledge | 1 | 38 | 177 | 142 | 6 |
| 产业链知识图谱 | 2 | 14 | 271 | 226 | 51 |
| AI Governance | 2 | 1,096 | 5,553 | 3,201 | 374 |

实体归一的实际结果：

| 项目 | 重复出现实体 | 多别名实体 | 跨文档实体 | 平均来源数 |
| --- | ---: | ---: | ---: | ---: |
| ICP-fault-knowledge | 0 | 0 | 0 | 1.00 |
| 产业链知识图谱 | 10 | 0 | 10 | 1.04 |
| AI Governance | 71 | 31 | 71 | 1.02 |

这些数据证明归一机制已经产生实际效果：AI Governance 中有 71 个规范实体被多个文档
共同支持，31 个实体保存了多个别名。但 3,201 个规范实体中只有 71 个跨文档复用，
其余绝大部分仍是单来源实体，说明漏合并、边界过细或一次性噪声实体仍然较多。

AI Governance 的 374 条有效关系中，关系类型分布为：

| 关系类型 | 数量 | 占比 |
| --- | ---: | ---: |
| `related_to` | 244 | 65.2% |
| `part_of` | 59 | 15.8% |
| `produces` | 23 | 6.1% |
| `causes` | 15 | 4.0% |
| `belongs_to` | 13 | 3.5% |
| `uses` | 11 | 2.9% |
| `depends_on` | 9 | 2.4% |

最近一次 AI Governance 单文档任务处理了 109 个知识块，最终同步 1,181 个实体和
118 条关系。任务日志同时记录“补抽取 29 个知识块，复核通过 0 条，拒绝 291 条”。
这说明实体发现覆盖较强，但关系复核通过率异常低；日志中的“候选、通过、拒绝”也没有
完整展示 deferred、missing response、terminal failure 和 quarantined 等去向，旧运行
版本的可观测口径不足以独立判断所有候选的最终状态。

## 4. 当前主要问题

### 4.1 实体边界和实体价值判断不足

- 部分完整定义、长修饰短语、标题或列表项被当成单个实体，实体边界过宽；
- 部分通用名词、结构词和一次性短语被保存为规范实体，形成大量低复用节点；
- 同一概念可能以长短不同、单复数不同或上下文附加词不同的形式重复创建；
- 类型判断仍会受局部上下文影响，同一概念在不同知识块中可能出现类型漂移；
- 当前抽取更偏向“尽量发现”，缺少独立的实体值得入图判定和边界精修阶段。

直接影响是规范实体数量膨胀、跨文档复用率偏低，并给后续候选召回、关系生成和社区检测
引入噪声。

### 4.2 实体归一仍以保守漏合并为主

- 精确名称、已有别名和稳定 assignment 的复用效果可靠，但只能覆盖明显相同实体；
- 语义候选虽经过 pgvector、reranker 和 LLM，真实跨文档合并数量仍然有限；
- 类型冲突、版本号、组织与产品同名等保护是必要的，但阈值过严时会造成漏合并；
- 相似长短语容易同时受到边界错误和语义相似影响，直接合并可能产生错误规范实体；
- 缺少经人工确认的 false merge、false split 样本，无法按实体类型可靠校准阈值。

当前应继续保持“歧义时拆分”的安全原则。优化重点不是放宽所有阈值，而是先改善实体
边界和类型，再按类型校准召回、重排与裁决门槛。

### 4.3 关系抽取召回偏低

- 实体数量远高于关系数量，很多有多个实体的知识块仍没有形成关系；
- 关系依赖局部证据和同一知识块上下文，跨句、跨知识块和跨章节关系容易遗漏；
- 补抽取能够增加候选，但不能稳定解决隐式关系、代词指代和长距离依赖；
- 部分关系候选只反映共现，缺少明确谓词和方向证据；
- 当前尚无跨知识块关系聚合阶段，文档级关系主要依赖各块结果的并集。

### 4.4 关系语义过于泛化

AI Governance 中 `related_to` 占 65.2%，说明大量关系没有落入更具体的领域谓词。
这种关系可以保持图连通，但对路径解释、因果分析、问答和社区语义贡献有限。原因包括：

- 逻辑 Schema 的关系类型不够覆盖实际表达；
- 抽取提示在不确定时倾向选择通用关系；
- 关系端点边界或类型不稳定，使具体谓词难以通过校验；
- 复核层对具体关系严格，而通用关系更容易被保留。

### 4.5 关系复核过严且可观测口径不完整

最近一次任务出现“复核通过 0、拒绝 291”，与最终仍发布 118 条关系并存。这可能同时
包含规则直接接受、旧策略保留、复核拒绝、缺失响应和未分类状态，但旧运行日志没有把
每种去向完整列出。

最新代码已经要求 overflow、deferred、missing response、terminal failure 和
quarantined 传播到 `coverage_complete=false`，并阻止 finalize、evaluate、quality gate、
`production_approved` 和 activate；但当前运行容器数据库结构尚未提供完整候选级审计，
需要升级运行环境后再验证实际闭环。

### 4.6 置信度尚未充分校准

现有关系中仍存在默认或集中在固定值附近的 confidence。该值不能直接解释为真实正确率，
也不能代替分关系类型的 precision/recall 校准。没有独立人工 Gold 时，模型自产标签不能
作为生产激活依据。

### 4.7 图结构质量受上游问题放大

- 漏合并会把同一概念拆成多个节点，形成多个局部星形子图；
- 错合并会把本不相同的实体连接到同一中心节点，污染所有相邻关系；
- 关系过少会使图稀疏，跨文档路径和社区结构不稳定；
- `related_to` 过多会提高表面连通性，却降低路径语义和可解释性；
- GraphRAG 社区检测只能忠实组织输入图，上游噪声会直接进入社区结果。

## 5. 已完成的关键保护

当前代码已经具备以下正确性与安全基础，不应在后续优化中回退：

- 实体提及使用稳定 `mention_key` 和精确半开字符位置；
- ingestion 重试优先复用已有 occurrence assignment；
- 精确、词法、向量、reranker 和 LLM 组成有界候选链路；
- PostgreSQL 批量精确候选按单请求最多 10 条截断；
- cannot-link 覆盖 redirect 旧节点和当前根节点，并在最终接受前重检；
- Unicode casefold 规范化，避免大小写和特殊字符处理不一致；
- 关系候选、批次和负载均有显式上限，不通过静默截断换取性能；
- 候选覆盖不完整时 fail-closed，不能晋级生产；
- active revision、策略版本、输入指纹和图 generation 用于隔离旧结果；
- P1/P2 treatment 继续保持 shadow，不覆盖 control；
- GraphRAG 社区结果保持 shadow，不影响现有检索和 HugeGraph 正式图。

## 6. 优化优先级

### P0：建立可度量的抽取和归一基线

1. 建立小规模人工 Gold，覆盖实体边界、实体类型、关系谓词、关系方向和跨文档同实体；
2. 按实体类型统计边界 precision/recall、false merge 和 false split；
3. 按关系类型统计候选、直接接受、复核通过、拒绝、延迟、缺失、失败和隔离；
4. 升级运行数据库到最新迁移，验证候选级审计和 `coverage_complete` 门禁。

### P0：改善实体和关系输入质量

1. 在主抽取后增加确定性的边界清理和实体值得入图过滤；
2. 对标题、定义句、列表项、版本号、组织名和复合名词分别制定可测试规则；
3. 关系候选优先使用明确谓词、方向词和同句/邻句证据，降低纯共现候选；
4. 对具体关系和 `related_to` 分开校准，避免用通用关系掩盖不确定性。

### P1：提高跨文档归一质量

1. 在人工 Gold 上按实体类型分别校准 pg_trgm、向量、reranker 和 LLM 阈值；
2. 建立人工复核队列，优先处理高频实体、高连接实体和分数临界候选；
3. 将人工 merge/split 结论沉淀为 must-link/cannot-link，参与后续增量入库；
4. 监控每新增文档产生的规范实体增量和跨文档复用率，识别实体爆炸。

### P1：提高关系表达能力

1. 根据代表性知识块和人工 Gold 增量扩充逻辑 Schema 的具体关系类型；
2. 对跨句关系引入受限窗口，不进行全项目实体两两组合；
3. 对重复关系进行证据聚合，保留多文档、多知识块支持数；
4. 对高价值关系类型设置独立复核提示和质量门槛。

P1/P2 新策略只有在独立人工 Gold 和完整覆盖门禁通过后才可讨论生产激活；当前仍是
shadow，不能宣称已经具备生产切换条件。

## 7. 建议验收指标

| 类别 | 指标 |
| --- | --- |
| 实体抽取 | 边界 precision/recall/F1、类型 macro-F1、每千 Token 有效实体数 |
| 实体噪声 | 单来源实体比例、低信息实体比例、实体提及/规范实体比 |
| 实体归一 | 跨文档复用率、false merge rate、false split rate、候选召回率 |
| 关系抽取 | 每类 precision/recall/F1、有关系知识块占比、每千 Token 有效关系数 |
| 关系语义 | `related_to` 占比、具体关系覆盖率、关系方向正确率 |
| 关系复核 | 通过/拒绝/deferred/missing/failure/quarantined 数量及覆盖完整率 |
| 来源质量 | 实体位置命中率、关系证据命中率、可追溯到文档和知识块的比例 |
| 图结构 | 跨文档边比例、孤立实体比例、连通分量数量、社区稳定性 |
| 运行安全 | 重试幂等率、旧 revision 泄漏数、coverage 不完整时错误晋级数 |

在没有人工 Gold 的情况下，只能确认工程链路、来源追溯和安全门禁是否正确，不能可靠
判断抽取、合并和关系发布的真实 precision/recall，也不能批准 P1/P2 生产激活。

## 8. 结论

Knowledge Forge 已形成完整且可审计的实体关系处理框架：实体发现覆盖较强，分层候选召回
避免了随项目实体总量平方增长，稳定 assignment、cannot-link 和 fail-closed 门禁解决了
多项数据正确性问题，跨文档实体归一也已产生真实效果。

当前质量瓶颈已经从“链路是否存在”转向“抽取和归一结果是否足够准确”：实体边界偏宽、
低复用实体偏多、跨文档漏合并仍明显、关系召回偏低、`related_to` 过多、关系复核通过率
异常低且旧运行环境的候选状态可观测不完整。下一步应以人工 Gold、候选级审计和分类型
指标为基础，先改善上游实体边界和关系证据，再校准归一与复核阈值，而不是直接放宽门禁。
