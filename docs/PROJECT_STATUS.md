# Knowledge Forge 项目现状、已完成功能与问题说明

## 1. 文档目的

本文档说明 Knowledge Forge 当前已经完成的能力、实际运行状态、知识抽取质量、
已知问题及后续优化方向。本文档将“功能已经实现”与“效果已经达到生产要求”分开描述，
用于开发维护、阶段汇报、测试验收和后续版本规划。

文档更新时间：2026-07-17。

## 2. 项目定位

Knowledge Forge 是一个通用、多项目的知识库与知识图谱构建平台。用户可为不同业务主题
创建独立项目，上传源文档，由系统自动完成文档结构解析、知识分块、向量索引、逻辑
Schema 评估、实体与关系抽取、跨文档实体归一及 HugeGraph 同步。

系统不依赖 RAGFlow 运行时，当前核心依赖如下：

| 组件 | 当前职责 |
| --- | --- |
| PostgreSQL + pgvector | 保存项目、文档、章节、知识块、向量、逻辑 Schema、实体、关系、来源和任务状态 |
| HugeGraph | 保存可遍历的物理知识图谱 |
| Ollama | 提供 LLM、Embedding 和视觉理解能力 |
| Docling/PyPDF/原生解析器 | 处理 PDF、Word、文本和表格文档 |
| KnowledgeFiles | 保存源文档、过程 JSON、图片和软删除文件 |

所有业务数据按 `project_id/project_key` 隔离。多个业务项目共享 HugeGraph 物理图
`knowledge_forge`，但不会互相混用实体和关系。

## 4. 已完成的完整处理链路

### 4.1 项目与模型配置

用户可以创建多个项目，并为每个项目选择 LLM 和 Embedding 模型。模型来自当前 Ollama
服务，页面可刷新本地模型列表。项目还可设置模型请求 Token 上限和单个知识块 Token
上限，这些参数只影响当前项目，不修改 Ollama 全局上下文配置。

### 4.2 文档上传与存储

上传文件最大为 200 MB。系统在项目内使用文件内容 SHA-256 去重，相同内容不能在同一
项目重复入库，但允许进入不同项目。

文件保存结构如下：

```text
KnowledgeFiles/
├── docs/<项目>/<文档>/       # 源文档
├── chunks/<项目>/<文档>.json # 结构块和知识块过程数据
├── media/<项目>/<文档>/      # 图片及图片分析缓存
└── .trash/                    # 软删除文件
```

### 4.3 结构解析

系统按文件独立选择解析器：

| 文件类型 | 主要处理方式 |
| --- | --- |
| DOCX | 使用 Word 原生段落、标题、表格和内嵌图片结构 |
| 普通 PDF | 优先使用 PyPDF 提取文本层和页码 |
| 扫描或复杂 PDF | 自动使用 Docling 进行版面、OCR 和表格解析 |
| Markdown/TXT | 使用文本原生结构和标题规则 |
| XLSX/XLS/CSV | 使用表格原生解析，保留工作表、表头和行数据 |

解析完成后，页面可查看结构块，检查标题层级、章节路径、正文、表格、页码和图片来源。

### 4.4 图片处理

扫描 PDF、普通 PDF 中的内嵌图片和 DOCX 内嵌图片会保存到 `KnowledgeFiles/media`。
图片经过尺寸过滤、OCR 和视觉 LLM 分析后形成带来源信息的图片知识。图片描述和 OCR
文字与正文一起参与分块、向量索引、实体抽取和关系抽取。

当前暂不支持将独立 PNG/JPG 作为源文档直接上传。

### 4.5 分块与向量索引

系统为每个文件自动选择分块策略，也允许用户上传时手动指定：

| 策略 | 主要行为 |
| --- | --- |
| 兼容分块 | 使用较通用的长度边界和重叠窗口 |
| 通用分块 | 保留标题层级和章节上下文 |
| 论文分块 | 区分摘要、正文、章节和参考文献 |
| 表格分块 | 按工作表和数据行切分，并重复必要表头 |

每个知识块会写入 PostgreSQL，并通过项目选定的 Embedding 模型生成向量。
向量保存为 pgvector `vector`，按模型和维度建立 HNSW 索引。联合检索会结合向量相似度、
关键词分数、完整短语命中及实体关系结果。

### 4.6 逻辑 Schema 评估

每个项目从通用基线 v1 开始。系统过滤封面、目录、过短内容和低信息知识块，再按章节
分层并使用向量多样性选择代表知识块。LLM 只能提出有证据的新增类型，不能自动删除、
重命名或改变已有类型含义。

Schema 具备以下能力：

- 按项目独立保存和版本化；
- 新文档与已有知识重复度较高时跳过无意义评审；
- 用户可手动重新评估当前项目 Schema；
- 删除全部文档后自动回退到通用基线 v1；
- HugeGraph 物理标签保持稳定，领域差异保存在 PostgreSQL 逻辑 Schema 中。

### 4.7 实体和关系抽取

当前采用“主抽取、针对性补抽取、规则检查、批量 LLM 复核”的流程：

1. LLM 从单个知识块抽取实体提及和关系候选；
2. 每个实体和关系必须携带能够在原文定位的证据；
3. 信息量较高但抽取为空的知识块执行一次针对性补抽取；
4. 系统校验实体是否真实出现、关系端点是否存在、类型是否符合 Schema；
5. 高置信且规则完整的关系直接接受；
6. 不确定关系交给 LLM 批量复核；
7. 最终结果保留项目、文档、知识块、证据文本和字符位置。

### 4.8 实体归一

实体归一按项目执行，当前候选处理链路如下：

```text
规范名称/别名精确匹配
→ PostgreSQL pg_trgm 名称候选
→ pgvector HNSW 语义候选
→ 类型、编号、版本和名称规则过滤
→ bge-reranker-v2-m3 重排
→ 高置信规则合并或 LLM 最终裁决
→ 无可靠候选时创建新实体
```

每次实体归一决策会写入 `entity_resolution_decisions`，保存候选、分数、决策方式、
模型和原因，便于后续审计。

### 4.9 HugeGraph 同步

当前 HugeGraph 使用稳定的物理结构：

```text
Vertex: KFDocument, KFChunk, KFEntity
Edge:   kf_contains, kf_mentions, kf_related
```

文档全部处理完成后会自动同步到 HugeGraph。Hubble 查询会限制当前项目，并展示文档、
知识块、实体和关系的来源路径。

### 4.10 任务与删除

处理任务保存于 PostgreSQL，而不是仅保存在 Web 进程内存。页面会分别显示：

1. 结构解析；
2. 分块及向量索引；
3. Schema 和基础图数据；
4. 逐块抽取实体与关系；
5. HugeGraph 同步。

删除文档时，系统会立即软删除文档并取消关联任务，使文档从列表和检索结果中消失；
后台清理任务随后处理 HugeGraph、源文件、过程文件、知识块、向量、实体提及和关系贡献。
如果服务重启，未完成的清理任务可以恢复执行。其他文档仍支持的规范实体不会被删除。

## 5. 数据与来源追溯

当前主要数据表如下：

| 数据表 | 作用 |
| --- | --- |
| `projects` | 项目、模型和项目级参数 |
| `documents` | 源文档、解析状态和路由结果 |
| `sections` | 文档结构块和章节 |
| `chunks` | 可检索知识块 |
| `vector_embeddings` | Chunk 和实体向量 |
| `graph_schemas` | 项目逻辑 Schema 版本 |
| `canonical_entities` | 项目内规范实体 |
| `entity_mentions` | 文档中的实体提及及证据 |
| `entity_resolution_decisions` | 实体归一审计记录 |
| `relation_assertions` | 带来源的关系断言 |
| `jobs` | 解析、清理和维护任务 |
| `models`、`settings` | 模型发现和系统配置 |

实体提及和关系断言均保留 `project_id`、`document_id`、`chunk_id`、证据文本及抽取版本。
因此系统可以区分“规范实体”和“某篇文档对该实体或关系的具体支持”。

## 7. 当前质量评估

### 7.1 实体发现

系统已经能够识别大部分核心概念、组织、标准、人物和业务术语，例如 NIST、AI RMF、
AI system、risk tolerance 和 AI actors。当前实体发现覆盖率较高，丰富知识块通常能够
抽取出多条实体提及。

主要问题是部分实体边界过长，或者将标题、完整定义、修饰性短语识别为独立实体。例如：

- `approaches that increase the trustworthiness of AI systems...` 被整体作为实体；
- `Risk management of AI systems that are intended to augment or replace human activity`
  被整体作为 Event；
- `Appendix ...`、`Table ...` 等结构标题被作为 GenericEntity。

结论：实体名称抽取基本可用，但还需要边界规范和低价值实体过滤。

### 7.2 实体类型

当前通用 Schema 的类型粒度有限，导致模型将不同性质的概念压入相近类型：

- `Risk management` 被标为 Technology；
- `water` 被标为 Location；
- `intended audience` 被标为 Person；
- `AI lifecycle` 同时出现 Technology 和 Event；
- `reliable metrics` 被标为 Product。

结论：实体类型质量低于实体名称质量，当前不适合直接依赖类型完成严格推理。

### 7.3 实体归一

本次快照中的 8 次规则自动合并经人工抽查，6 次合理、2 次明显错误：

合理案例：

- `AI RMF` 合并到 `Artificial Intelligence Risk Management Framework`；
- `AI systems` 合并到 `AI system`；
- `organization` 合并到 `organizations`；
- `AI actor` 合并到 `AI actors`。

错误案例：

- `Part 1` 被合并到 `PDF 第 1 页`；
- `risk measurement` 被合并到 `Risk management`。

同时仍存在名称完全相同但类型不同的重复实体：

- `AI RMF Playbook` 同时是 Product 和 Technology；
- `Framework` 同时是 Technology 和 Product；
- `AI lifecycle` 同时是 Technology 和 Event；
- `AI technologies` 同时是 Technology 和 Product。

结论：分层候选召回和重排链路已经生效，但类型不一致会阻止正确合并，语义相近也可能
导致错误合并。当前归一策略属于“可工作但仍需校准”。

### 7.4 关系准确性

当前存在较合理的关系：

- `Core part_of Framework`；
- `National Institute of Standards and Technology produces AI RMF`；
- `Artificial Intelligence Risk Management Framework uses risk management processes`；
- `organizations uses existing regulations and guidelines`。

也存在类型、方向或语义不正确的关系：

- `AI system causes inequitable outcomes`，但原文实际表达 AI 系统可以缓解不公平结果；
- `NIST produces evaluation`，原文实际是 NIST 执行评估；
- `potential negative impacts part_of threats`，上下位方向不正确；
- `Inscrutable AI systems causes Risk management`，原文实际表示增加风险测量难度。

部分 `related_to` 关系语义不算错误，但过于宽泛，难以支撑精确推理。

结论：如果只用于图谱浏览和候选关系展示，当前结果具有一定价值；如果要求关系谓词、
方向和因果语义准确，当前质量尚未达标。

### 7.5 关系召回

检查时只有 12/27 个已处理知识块生成关系。部分封面和目录块没有关系是合理的，但也有
明显漏抽取案例：一个包含 46 个实体提及的正文知识块描述了风险组成、AI 影响、风险管理
作用和可信 AI 等多组明确关系，最终生成了 0 条关系。

结论：关系召回率明显偏低，针对性补抽取尚未稳定解决富文本知识块漏关系的问题。

### 7.6 关系复核

检查时已保存的 32 条关系全部为 `evidence_unverified`，没有任何关系被 LLM 复核结果
明确标记为通过。当前实现会在复核器没有返回某候选的明确决策时，根据原文证据保留部分
候选，因此关系仍可进入数据库，但其质量状态没有真正闭环。

日志中的“候选数”不一定等于“通过数 + 拒绝数”，原因是还有一类“复核器未明确回答，
但因存在证据而回退保留”的关系没有单独显示在日志中。

结论：证据保留机制避免完全丢失关系，但当前关系验证机制没有达到预期效果。

### 7.7 当前主观评分

以下评分来自当前运行样本的工程抽查，不是基于标准标注集计算的正式指标：

| 质量维度 | 当前评价 |

| 实体边界 | 5 / 10 |
| 实体类型 | 4 / 10 |

## 8. 当前已知问题

### 8.1 高优先级问题

| 问题 | 当前影响 |
| --- | --- |
| 关系复核没有产生明确通过结果 | 数据库中的关系普遍停留在 `evidence_unverified` |
| 关系漏抽取 | 富文本知识块可能抽取大量实体但没有关系 |
| 关系谓词和方向错误 | 图谱遍历可能得出错误语义结论 |
| 回退保留规则偏宽 | 复核器未明确回答时，部分弱关系仍会进入数据库 |

### 8.2 中优先级问题

| 问题 | 当前影响 |
| --- | --- |
| 实体类型不稳定 | 同一实体可能因类型不同而重复创建 |
| 实体边界过长 | 图谱中出现整句、标题和定义型低价值实体 |
| 实体误合并 | 语义相关但身份不同的概念可能被合并 |
| 同名实体漏合并 | 类型冲突阻止完全相同名称的实体统一 |
| 置信度未校准 | 大量实体和关系使用默认 0.5，不能真实反映质量 |
| 关系复核日志不完整 | 无法直接看到每条候选被接受、回退或拒绝的原因 |
| 当前跨文档测试不足 | 最新链路还需要在多篇同领域文档上完成完整验证 |

### 8.3 较低优先级限制

| 限制 | 说明 |
| --- | --- |
| 独立 PNG/JPG 暂不支持上传 | 当前仅处理 PDF 和 DOCX 中的图片 |
| Schema 重评估不会自动重抽历史图谱 | 重评估后需明确触发重建，才能让旧实体关系使用新 Schema |
| 超高维向量不建 HNSW | 超过当前索引维度上限时使用 pgvector 精确检索 |
| Docling 首次运行依赖模型缓存 | 离线部署需要提前准备 Docling 模型缓存 |

## 9. 已解决的重要工程问题

以下问题已经在当前版本中处理，不再作为主要缺陷：

- 项目、文档、向量和图谱数据已实现项目级隔离；
- 相同文档在项目内按内容 Hash 去重；
- 多文件上传改为逐文件顺序执行，避免模型并发争用；
- 任务状态持久化，页面切换后仍可查看实时进度；
- 任务拆分为五个子阶段，各自显示进度；
- 结构块和 Chunk 中间结果可在页面查看；
- 文档完成后自动同步 HugeGraph，不再要求手动点击同步；
- Hubble 可直接打开当前项目查询并自动执行；
- PDF/DOCX 图片可进入 OCR、视觉理解和统一知识抽取流程；
- Docling 支持 GPU，并在低显存或 OOM 时回退 CPU；
- 文档删除增加软删除、任务取消、进度提示和持久化后台清理；
- 删除最后一篇文档后逻辑 Schema 自动恢复基线 v1；
- Ollama 项目上下文预算不再修改 Ollama 全局上下文配置。

## 10. 后续优化建议

### 10.1 第一优先级：关系质量闭环

1. 将关系复核结果拆分为“明确通过、规则通过、证据回退、明确拒绝、复核失败”。
2. 为每条候选保存源实体、谓词、目标实体、证据、判定原因和复核原始结果。
3. 复核模型遗漏候选时不再默认宽松接受，区分“模型调用失败”和“模型明确未支持”。
4. 对关系类型增加同义谓词映射、方向约束和起止实体类型约束。
5. 采用固定实体 ID 的二阶段关系抽取，避免模型重新生成不一致的实体名称。
6. 对富文本但零关系的知识块改进针对性补抽取，并限制只补充有原文证据的关系。

### 10.2 第二优先级：实体类型和归一

1. 同名实体先执行跨类型一致性检查，再决定合并或保留多义实体。
2. 增加实体边界清洗，过滤章节标题、整句定义和无业务意义的视觉装饰元素。
3. 完善通用 Schema 类型，减少 Person、Product、Technology 和 GenericEntity 的误用。
4. 为误合并样例建立负例测试，重点覆盖页码、章节、risk measurement/risk management、
   组织上下级、标准版本和产品系列。
5. 校准规则阈值、重排分数和 LLM 裁决门槛。

### 10.3 第三优先级：质量评测与可观测性

1. 建立人工标注的小型金标准数据集，覆盖通用、论文、表格和图片知识。
2. 分别计算实体边界、实体类型、实体归一、关系类型和关系方向的 Precision/Recall/F1。
3. 在任务页面增加质量汇总：候选数、通过数、回退数、拒绝数、补抽取数和失败数。
4. 增加实体归一与关系审核页面，支持查看原文证据和人工修正。
5. 使用两篇以上同领域文档持续测试跨文档实体共享和删除后的图谱贡献变化。

## 11. 建议验收指标

以下为进入“可稳定业务试用”阶段的建议指标，并非当前已经达到的结果：

| 指标 | 建议目标 |
| --- | ---: |
| 实体边界 Precision | 不低于 85% |
| 实体类型准确率 | 不低于 80% |
| 明确实体误合并率 | 不高于 2% |
| 关系严格 Precision | 不低于 80% |
| 关系 Recall | 不低于 70% |
| 关系证据覆盖率 | 100% |
| 关系判定状态完整率 | 100% |
| 同项目同名同义重复实体率 | 不高于 3% |
| 文档和知识来源可追溯率 | 100% |

上述指标应在人工标注测试集上计算，不能使用实体数量或关系数量代替质量指标。

## 12. 当前阶段结论

Knowledge Forge 已经完成从多格式文档上传、结构解析、分块、向量知识库、逻辑 Schema、
实体关系抽取、实体归一、HugeGraph 同步、联合检索到删除维护的完整工程链路。系统架构、
数据来源追溯、项目隔离和任务可靠性已经具备较好的基础。

当前主要瓶颈已经从“链路是否能跑通”转移到“抽取结果是否足够准确”。实体发现具有一定
可用性，但实体类型、实体归一、关系精确语义和关系召回仍需要系统优化。下一阶段应优先
建立可审计的关系验证闭环和标准质量评测集，再据此调整抽取提示、规则、模型和阈值。
